# ADR-0002: GitHub App, not OAuth app; import shape

**Status:** Partially implemented — Contents:Read clone + Contents:Write push-back both shipped (see Amendments below); webhooks and product-UI push-status surfacing remain future work
**Date:** 2026-07-11

## Context

forkai-code needs to read a user's repository and, once ADR-0001's real runtime lands, push commits an agent makes inside a server-side sandbox. It also needs a way to seed a map from an *existing* repo rather than starting from an empty one. Two GitHub auth models were considered: a classic OAuth App (long-lived user access token, coarse `repo` scope) or a GitHub App (fine-grained per-repo installs, short-lived installation tokens).

## Decision

**GitHub App.** Installation is per-repo (or per-org, user's choice at install time), and every push from the sandbox uses a short-lived installation token minted server-side at run start — the sandbox never holds a long-lived user token. Webhooks on the installation sync external commits (pushed outside forkai-code) back into the map.

The existing Notion module (`apps/api/src/notion/` in fork.ai) is the wiring template: a dedicated module owning OAuth/installation token storage and a callback controller. The flow itself differs — GitHub App installation is a redirect carrying an `installation_id`, not a user-scoped OAuth token exchange — but the shape (module boundary, token table, callback endpoint) carries over directly.

**Import-existing-repo flow:**

```
POST /projects/import { installationId, owner, repo, branches?, depth? }
  → one BRANCH node per requested branch (default: default branch only)
  → one CODE node per recent commit on each branch, flagged imported: true
      - no AgentRun row (nothing ran)
      - commit pill deep-links to the real GitHub commit, not a local diff view
  → one root learn node, generated by a single LLM call over the README + file tree
```

`depth` bounds how many recent commits are imported per branch (avoids seeding a map with years of history from one call).

## Alternatives considered

- **OAuth App:** simpler to stand up, but the access token is long-lived and scoped to everything the user can touch (`repo` scope has no per-repository restriction). Rejected — a sandbox that can push code should hold the narrowest, shortest-lived credential available, and only for repos the user explicitly installed the app on.
- **PAT (personal access token) pasted by the user:** zero integration work, but puts long-term token custody and rotation on the user and gives forkai-code no per-repo install/uninstall UX. Rejected as a permanent design; may be an internal-only fallback during early development.

## Consequences

- The `imported` flag is already present in the MVP Node schema (used today to mark seeded/non-agent nodes), so shipping this import flow requires no schema migration.
- Imported CODE nodes have no AgentRun — any UI that assumes "every CODE node has a run transcript" must branch on `imported` before trying to render one.
- Webhook-driven external-commit sync is out of scope for the import flow itself; this ADR only commits to the auth model and the one-shot import shape.

## Amendment (2026-07-13)

**Minimal GitHub App slice shipped — Contents:Read only, no webhooks, no push-back.** This landed alongside cloud-runner productization (ADR-0001's amendment) once a private repo became reachable via `environment: 'cloud'`: `CloudAgentRunner` clones through the sandbox's public network, so a private repo needs a real credential handed to `git clone`, not just an OAuth token sitting in DynamoDB.

**This coexists with, rather than replaces, the classic OAuth App this ADR originally rejected.** `GithubService` (OAuth, `scope: repo`, long-lived per-user token) is unchanged and still does all read-only browsing/import work (`listRepos`, `getRepoSeed`, `repo-import.service.ts`) — the Decision section's "every push from the sandbox uses a short-lived installation token" is what's new, not a replacement of the read path. The two auth models now serve genuinely different jobs: OAuth reads on behalf of the user's own GitHub identity (browsing, history import); the App mints a token scoped to exactly one repo for exactly one sandbox run.

**Shipped:**
- `GithubAppService` (`apps/code-api/src/github/github-app.service.ts`): `appJwt()` hand-signs an RS256 App JWT with `node:crypto` (`createSign` — no `jsonwebtoken`/`jose` dependency was added; neither is declared in code-api's `package.json`, same "no new SDK for one endpoint" call as the GLM provider's raw `fetch` usage). `verifyAndStoreInstallation` confirms the App can see the installation (`GET /app/installations/:id`) before persisting it. `mintInstallationToken(sub, owner, repo)` finds the caller's installation covering `owner` (case-insensitive login match) and mints a token scoped to just that one repo (`POST /app/installations/:id/access_tokens` with `{ repositories: [repo] }`), cached in-memory per `installationId:repo` until 5 minutes before its 1h expiry.
- Routes: `GET /github/app/install` (`@Public()` — installation itself doesn't need to know which forkai user is installing; the association happens at the callback) 302s to `https://github.com/apps/<slug>/installations/new`. `POST /github/app/installations` (authed) persists the installation against the caller's `sub` once the frontend's `/github/setup` page (reads GitHub's `?installation_id=` redirect) POSTs it.
- Storage: `GithubInstallationItem`, `PK: USER#<sub> SK: GHINST#<installationId>`, `{ installationId, accountLogin, createdAt }` — a user can hold more than one (one row per org/account they installed the App on).
- `RepoRef` gains `private?: boolean` (nested-object schema field, mirroring how `repoRef.owner`/`.repo` etc. are already declared — see root CLAUDE.md's "saveUnknown" gotcha). Set at project-create time from the value the frontend already has in hand from `GET /github/repos` (GitHub's own `private` field) — **not** re-fetched server-side. This is a trust boundary tradeoff: a client could lie and claim a private repo is public. The consequence of that lie is a failed `git clone` inside the sandbox (no credential embedded, repo returns 404 to an anonymous clone) — not a security hole, since the sandbox never gets a credential it wasn't explicitly minted. Re-verifying server-side (an extra GitHub API call per project create) is the honest v1.1 fix if this proves to matter in practice.
- `NodesService.resolveRunRepo` (was the env-plumbed `LOCAL_AGENT_REPO_PATH`/`_URL` block) branches on `repoRef.provider`: `'github'` + private → `mintInstallationToken` → `https://x-access-token:<tok>@github.com/<owner>/<repo>.git`, no installation covering the owner → `BadRequestException` telling the user to install the App; `'github'` + public → plain `${url}.git`; `'github-mock'` → no repo (an explicit `environment: 'cloud'` request 400s instead of silently running against nothing); `'new'` → `{ init: { defaultBranch } }`, handled by ADR-0001's `runner.mjs` (see that ADR's amendment).
- **Token redaction is unchanged and still covers the new path**: `runner.mjs`'s `redact()` strips `https://<token>@` from any git-command error text before it reaches an SSE frame or a log line — this applies identically whether the embedded credential is an installation token or (hypothetically) anything else, since the git clone command line is what's being redacted, not the credential's provenance.

**v1 = clone-only, same as ADR-0001's cloud runner in general** — the commit died with the machine (or survived only until the TTL sweep reaped the sandbox) until v1.1 shipped. **v1.1 = push-back** is now implemented — `Contents:Write` permission on the App (user-granted in GitHub's UI), `git push origin <branch>` in `runner.mjs` after the commit, using the same installation-token clone URL (a token minted with `repositories: [repo]` and `Contents:Write` can push to that one repo). This was the priority follow-up noted in the A2 plan and in ADR-0001's amendment ("Known gaps → follow-ups"); see the second Amendment below for the concrete mechanism, the no-remote/no-permission-yet fallback, and what's still blocked on live verification.
- **Not shipped, deliberately deferred:** webhooks (external-commit sync back into the map — this ADR's original Decision section scoped it in, but nothing in the minimal slice needs it), the `POST /projects/import { installationId, ... }` shape above (import still runs entirely over the OAuth path, unchanged), and any UI entry point into `/github/app/install` beyond the raw URL (no "Install GitHub App" button was added to `NewProjectModal` — activation is a manual link today, see `docs/forkai-code/deploy-cloud-runner.md`).

## Amendment (2026-07-13, second) — v1.1: push-back

**Push-back is implemented.** A cloud run's commit no longer necessarily dies with the sandbox: after `runner.mjs`'s existing post-run `git commit` (unchanged — only fires when the tree is dirty; the "no changes" case, `sha === baseSha`, is untouched and still skips both commit and push), it now attempts `git push origin <branch>` against the same `origin` remote git itself recorded at clone time — i.e. the same `https://x-access-token:<token>@github.com/<owner>/<repo>.git` installation-token URL `NodesService.resolveRunRepo` already builds for a private repo. No new credential is minted and no URL is reconstructed: `git push origin <branch>` reads the token straight back out of the `origin` remote config, the same way any `git push` on a normal clone does.

**Never blocks or fails the run.** The push attempt is fully isolated from the run's success/failure path:
- **No remote → silent no-op, not a warning.** `pushToOrigin()` first checks `git remote get-url origin`; when it fails (confirmed by reading `runner.mjs`'s `'new'`-project branch — `git init -b <branch>` never runs `git remote add`, so a `'new'`-project run genuinely has zero remotes), the function returns `{ pushed: false }` without attempting a push or emitting any event. This is the expected shape for that flow, not an anomaly worth surfacing.
- **Any push failure → `warn` SSE event + `pushed: false`, run continues normally.** Auth failure (App/token lacks `Contents:Write`, e.g. an installation the user hasn't re-approved yet after widening the App's permission), a non-existent remote branch, or a non-fast-forward rejection are all caught the same way — `git push` without `--force` fails naturally on non-fast-forward, so no special-case detection was needed, and **force-push was not added, even as a fallback**, per this ADR's own scope. The error text is redacted through the same `redact()` helper already used for clone errors before it reaches the `warn` SSE frame or the final `result` frame's `pushError`.
- **30s timeout.** `run()` (the sandbox's generic subprocess helper) gained an optional `timeoutMs` that `SIGKILL`s the child and rejects with a redacted message on expiry — `git push` is called with `timeoutMs: 30_000` so a stalled network call can't hang the whole run.

**Result frame extended.** `runner.mjs`'s final `result` SSE event now carries `pushed: boolean` always, plus `pushError?: string` (redacted) when a push was attempted and failed — alongside the existing `sha`/`baseSha`/`diffSummary`/`exitCode`. `CloudAgentRunner` (`apps/code-api/src/agent/cloud/cloud-agent-runner.ts`) parses both off the frame; `AgentRunFinal` (`apps/code-api/src/agent/agent-runner.ts`) gained matching optional `pushed?: boolean` / `pushError?: string` fields, set directly from the sandbox's report. **This is round-trip plumbing only — nothing renders it yet, and it is not persisted to `NodeItem`/Dynamo.** The next small step (explicitly not done here, to keep this change to push mechanics only) is surfacing it in product UI — e.g. a "pushed to GitHub ✓" vs "commit only, in sandbox" pill on the commit — and, separately, deciding whether that state needs to survive past the live SSE stream (a Dynamo field) once there's a UI consumer for it.

**Confirmed, not assumed, before writing any of this:** `GithubAppService.mintInstallationToken` (`apps/code-api/src/github/github-app.service.ts`) sends only `{ repositories: [repo] }` in its `POST /app/installations/:id/access_tokens` body — no `permissions` field — so a minted token's permission set is whatever the App itself is configured with for that installation. This confirms no code change was needed to make push *possible*: the capability change is purely the App's own `Contents:Write` permission grant, made in GitHub's UI by the user. One caveat this doesn't cover: GitHub requires an *existing* installation to be re-approved by the account admin after the App's permission set widens, before a token minted against it actually carries `Contents:Write` — forkai-code has no code path that detects a stale, not-yet-re-approved installation and prompts for re-approval; a push against one will simply fail through the generic warn-and-continue path above.

**`LocalAgentRunner` is untouched, deliberately — not an oversight.** It has no GitHub App token to push with (it clones from `LOCAL_AGENT_REPO_PATH`/`_URL`, a local filesystem path or a plain URL, never an installation-token credential), and push-back for the dev-only local path was already scoped out by ADR-0001's original "real lineage requires real runs from node 1" gap, which is a separate, deliberate, dev-only limitation from the cloud/GitHub-App-backed path this amendment covers.

**Verified:**
- `node --check infra/sandbox-image/runner.mjs` — clean.
- `npx nx test @fork-ai/code-api` — 479/479 passing (26 suites), including 3 new `CloudAgentRunner` cases: push success reaches `AgentRunFinal.pushed`, push failure/no-remote reports `pushed: false` with the run still completing successfully (sandbox not destroyed over a push failure), and redaction holding on `pushError` end-to-end (asserts no `x-access-token`/`ghs_`/`github_pat_` pattern survives).
- `npx nx build @fork-ai/code-api` — clean.
- `docker build --platform linux/amd64 infra/sandbox-image` — builds successfully (local sanity check only; the image was not pushed to any registry).

**Not verified — blocked on live GitHub App credentials and a real installed repo with `Contents:Write`, neither of which exist in this environment.** No actual `git push` has run against a real GitHub remote. Once both exist, the check is: (1) run a cloud CODE node against that repo through the normal product flow, (2) confirm the SSE stream's final `result` frame reports `pushed: true` with no `pushError`, (3) `git log` on the real remote branch (or the GitHub commits UI) shows the new commit, matching the `sha` the app reported, (4) as a negative-path check, run once against a repo/installation that only has `Contents:Read` (or hasn't been re-approved after the permission widen) and confirm `pushed: false` plus a redacted `pushError` in a `warn` event, with the run still completing normally end-to-end rather than erroring out.
