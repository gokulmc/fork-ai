# ADR-0007: Repo creation via prefilled github.com/new + auto-attach

**Status:** Backend shipped (installation `repository_selection` capture + rootQuery seeding for github-provider projects); frontend create-repo flow ships concurrently
**Date:** 2026-07-20

## Context

Today a project's `repoRef.provider` is either `'new'` (no repo at all — forkai-code never talks to GitHub) or `'github'`/`'github-mock'` (attach an existing repo, imported via `RepoImportService`). There's a gap in between: a user who wants a *real* GitHub repo but doesn't have one yet has to leave forkai-code, create it manually on github.com, then come back and attach it.

The obvious fix — create the repo server-side — runs into a GitHub API limitation. forkai-code's GitHub App (ADR-0002) authenticates as an **installation** (server-to-server), and installation tokens cannot create repositories on a personal account: `POST /user/repos` only accepts a user-token (OAuth user-to-server, or a PAT). Creating on an *organization* installation is possible via `POST /orgs/{org}/repos`, but only with the App's `Administration:write` permission — a permission this App doesn't hold today, and personal accounts (the common case) aren't covered by it regardless.

## Decision

**Prefill `https://github.com/new` and auto-attach.** The frontend opens `https://github.com/new?owner=…&name=…&description=…&visibility=private` in a new tab; the user completes creation on github.com (a page they already trust, with GitHub's own name-collision/validation UX for free); forkai-code then polls `GET /github/repos` until the new repo appears in the installation's repo list, and attaches it automatically — no manual "paste the URL back" step.

This is seamless only when the installation's repository access is **All repositories** — a repo created after install is visible immediately. If the installation is scoped to **selected repositories**, a freshly created repo is invisible to the App until the user manually adds it in GitHub's settings, and polling would hang. GitHub has no URL parameter or API to force "All repositories" as part of an installation or a repo-creation call, so the product compensates on three fronts instead:

1. **Ask at install time** — the App install copy (`/github/setup`) recommends "All repositories" so most users never hit the selected-repos case.
2. **Store `repository_selection` per installation** — `GithubAppService.verifyAndStoreInstallation` now persists the App's own `repository_selection: 'all' | 'selected'` (from `GET /app/installations/:id`) and `account.type` (`'User' | 'Organization'`) onto `GithubInstallationItem`. `listInstallations` returns them per-installation so the frontend knows, before the user even opens the create-repo flow, whether the nudge is needed.
3. **Nudge at the moment of need** — if the installation is `'selected'`, the frontend deep-links to the installation's settings page instead of (or alongside) `github.com/new`: `https://github.com/settings/installations/{id}` for a `User` account, `https://github.com/organizations/{login}/settings/installations/{id}` for an `Organization` (GitHub's own URL shape differs by account type, hence storing `accountType`). GitHub's installation settings page supports "Redirect on update," which bounces the user back through `/github/setup` — the existing install-callback route — which re-fetches and re-stores the installation, so the stored `repositorySelection` is fresh by the time the create-repo flow resumes.

**Legacy rows self-heal lazily.** Installations stored before this change lack `repositorySelection`/`accountType`. Rather than a backfill migration, `listInstallations` does a live `GET /app/installations/:id` per row missing the field (a user holds at most 1-2 installations, so this is cheap) and re-persists the fresh values. If that live call itself fails, the row is still returned — not dropped — with conservative defaults (`accountType: 'User'`, `repositorySelection: 'selected'`); 'selected' is the safe assumption on a failed lookup since it only ever adds a nudge, never silently over-grants trust.

## Alternatives considered

- **`Administration:write` App permission, then `POST /orgs/{org}/repos` / equivalent.** Would let the App create the repo directly with no github.com hop and no all-vs-selected ambiguity. Rejected for now: it's an org-only capability (still doesn't solve personal-account creation), it's a heavier permission grant than anything the App holds today (repo creation/deletion, not just content read/write), and — per GitHub's App model — **every existing installation would need to be re-approved** by its account admin before a token minted against it actually carries the new permission (the same re-approval gap ADR-0002's second amendment already documents for `Contents:Write`). Revisit if the github.com-hop UX proves too rough in practice.
- **App user-to-server OAuth** (the App's own short-lived, user-scoped token flow — distinct from the classic OAuth App). `POST /user/repos` accepts this token type, so it would enable direct creation without the `Administration:write` grant. Short-lived tokens keep this in principle acceptable under this ADR's own auth posture. Kept as the fallback of choice if the github.com hop is rejected later — but not adopted now, since it reintroduces a user-token surface in the app immediately after ADR-0002's 2026-07-20 amendment removed the classic OAuth App for exactly that reason (narrower credential surface). Revisiting this trades one narrow surface (github.com hop, zero new credentials) for another (short-lived user token, one new OAuth flow) — not an obviously free win today.

## Consequences

- `GithubInstallationItem` gains `accountType?: 'User' | 'Organization'` and `repositorySelection?: 'all' | 'selected'` (both optional, for the legacy-row self-heal above). `GithubInstallationSchema` declares both (`saveUnknown: false` — an undeclared field is silently dropped on write and read, per root `CLAUDE.md`'s standing footgun note).
- `GithubAppService.listInstallations`'s return shape changes from `{ configured, installed, accounts: string[] }` to `{ configured, installed, installations: Array<{ installationId, accountLogin, accountType, repositorySelection }> }` — a breaking shape change on `GET /github/app/status`, coordinated with the concurrent code-web change that consumes it.
- `ProjectsService.buildSession`'s import rule becomes "rootQuery present → skip import, seed with rootQuery": a `'github'`-provider project created with a `rootQuery` (i.e. via this create-repo flow, on a repo that has no history yet) now takes the same BRANCH-root fill-root seed path as provider `'new'`, instead of attempting `RepoImportService.buildImportedNodes` against a repo that — moments after creation — has at most one commit. Attach-existing projects never send `rootQuery`, so that import path is unchanged.
- **"Add a README" guidance is needed in the frontend's create-repo copy.** github.com/new lets a user create a genuinely empty repo (no commits at all). An empty repo already degrades gracefully on the *import* path (`ProjectsService.buildSeed`'s try/catch → synthesized seed, same as any other empty-repo case) — but the *first push* from a subsequent cloud CODE run against a truly empty remote (no default branch ref yet) is untested end-to-end. Until that's verified, the product should steer users toward checking "Add a README file" on the github.com/new form.
