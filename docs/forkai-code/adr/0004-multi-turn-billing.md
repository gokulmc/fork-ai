# ADR-0004: Billing for agentic runs

**Status:** Implemented — against a redesigned shape (see Amendment 2026-07-13); the per-turn billing + between-turn ceiling design below was not built as written
**Date:** 2026-07-11

## Context

fork.ai's billing model — fork.ai ADR-0004 (`docs/adr/0004-credit-billing-model.md`) and fork.ai ADR-0009 (`docs/adr/0009-branch-output-budget-non-streaming-ceiling.md`) — was built for one short, single-shot LLM call per node: check credit `> 0` before the call (no pre-auth), deduct post-hoc from the returned token usage, and cap output at a fixed non-streaming ceiling (16K tokens). None of this holds for a `code` node once it's a real multi-turn agent run: a run can span dozens of turns, each with its own tool calls, over minutes, and a single pre-run credit check gives no protection against a run that burns through the user's entire balance mid-flight.

## Decision

For when a real runtime (ADR-0001) lands:

1. **Per-turn billing, not per-run.** Each agent turn writes its own `billUsage` row (same shape as today's Usage Event), all sharing a new `runId` field that ties every turn back to the same `AgentRun`. This replaces "bill once at the end" with "bill continuously as the run progresses."
2. **A per-run budget ceiling, checked between turns.** Before starting the next turn, the runner checks accumulated spend on `runId` against a configured ceiling. Exceeding it aborts the run (no further turns started) rather than blocking retroactively — a run cannot be billed past its ceiling by more than one turn's worth of overshoot.
3. **A pre-auth credit hold at run start.** Unlike fork.ai ADR-0004's "check `> 0`, deduct after," a multi-turn run reserves an estimated amount off the user's credit balance before the first turn, released/reconciled against actual per-turn spend as the run completes or aborts. This bounds worst-case exposure from a single run in a way a post-hoc-only model cannot.
4. **Running cost surfaced live.** The agent-log header (the streaming SSE view of a run) shows accumulated spend so far, updated per turn — the multi-turn equivalent of fork.ai's post-call cost display, but visible *during* the run instead of only after.
5. **Hold reconciliation on run end.** Whether a run completes, is aborted by the ceiling, or errors out, the pre-auth hold is reconciled against the sum of its per-turn `billUsage` rows: unused hold is released back to the balance, and any turn-level shortfall (a turn costing more than the remaining hold covered) is deducted directly, mirroring how fork.ai ADR-0004 already tolerates a small over-draft window rather than adding conditional-write locking.

This is deliberately scoped to `kind: CODE` only — `learn`, `plan`, and `branch` nodes remain single-shot LLM calls and keep billing exactly as fork.ai ADR-0004 describes today; nothing here changes their path.

## Alternatives considered

- **Keep post-hoc-only billing, just bill once at run end:** simplest, no new fields. Rejected — this is exactly the unbounded-overshoot problem in the Context; a long run could exhaust a user's balance many times over before the first (and only) bill lands.
- **Hard pre-auth for the full estimated run cost, no per-turn billing:** simpler settlement, but agent run length is inherently unpredictable (unlike a single structured-JSON call), so any fixed pre-auth estimate is either too conservative (blocks runs that would've finished cheaply) or too loose (defeats the point). Rejected in favor of the hold-plus-per-turn-reconciliation combination.
- **No budget ceiling, rely on pre-auth hold alone:** simpler, but a hold sized for "worst case" would need to be very large to avoid false-blocking; a between-turn ceiling check catches runaway runs without requiring an oversized hold.

## Consequences

- This **partially supersedes fork.ai ADR-0004** for `kind: CODE` runs only — the credit-balance-as-source-of-truth model, the Usage Event log shape, and the Credit Multiplier all carry over unchanged; only the "check once, bill once" cadence changes for agent runs.
- fork.ai ADR-0009's non-streaming 16K ceiling does not apply to agent turns the same way — each turn is itself a bounded call, but a run's *total* output is unbounded by turn count, which is exactly what the per-run budget ceiling in point 2 exists to bound instead.
- `UsageEvent` gains an optional `runId` field. Per the `saveUnknown: false` gotcha (see root CLAUDE.md), this field must be declared on the schema before any code sets it, or it silently drops on write.
- The budget ceiling (point 2) and the sandbox infra cost noted in the runtime ADR are two independent costs of the same run — a ceiling tuned only to LLM token spend would under-protect against a run that is cheap on tokens but expensive on wall-clock sandbox time. The ceiling check should account for both once real per-second infra pricing is known.

## Amendment (2026-07-13) — implemented against single-shot reality

**The original per-turn design above was unbuildable.** It assumed the API could observe and gate individual agent turns — check accumulated spend on `runId` *between* turns, abort before starting the next one. A cloud run doesn't work that way: the sandbox fires one `claude -p` invocation for the whole run and the API can only watch its SSE output stream; there is no between-turn boundary the API controls or can intervene at. Per-turn `billUsage` rows and a between-turn ceiling check were both replaced by the design below once this became clear against the real runtime (ADR-0001).

**What shipped instead — three parts:**

1. **Strict pre-auth hold (API-side).** `UsersService.placeHold` performs one atomic conditional deduct — `DynamoRepository.deductCreditIfSufficient` (`$ADD creditUsd -hold` with condition `attribute_exists(...) AND creditUsd >= :hold`) — which *is* both the strict gate (402 Payment Required on insufficient balance) and the reserve, in a single op. This closes the concurrent-overdraft TOCTOU a separate "check then deduct" would have (two concurrent cloud runs each reading a stale balance and both passing). The reserve is recorded as a `HoldItem` (`PK: USER#<sub>`, `SK: HOLD#<nodeId>`), lifecycle `held → reconciled`, flipped via a second conditional update (`DynamoRepository.reconcileHoldStatus`) that is the exactly-once settlement guard — a run's own done/error path and a concurrent sweep tick can both race to reconcile the same hold, and only the winner of the conditional flip settles it. A 30-minute `UsersService.reconcileStaleHolds` sweep releases holds orphaned by a crashed run (no done/error ever reached).
2. **Native budget ceiling (sandbox-side), replacing per-turn billing's job.** Instead of the API metering and gating turns, the API computes a ceiling (`min(MAX_RUN_COST_USD, balance)`, from `placeHold`) and passes it to the sandbox as `--max-budget-usd` (converted from billed dollars to raw model-cost dollars by dividing out `creditMultiplier`) alongside `--model`, both flags on the `claude` CLI invocation itself. Claude enforces its own cost cap natively and stops the run with a `result` line of `subtype: 'error_max_budget_usd'` (`runner.mjs` sets `budgetExceeded = true` on seeing it). This replaced a hand-rolled per-message output-token meter that live testing proved couldn't work: `stream-json`'s per-message `usage.output_tokens` are placeholder values (observed 1–3 regardless of actual output length) — the real cost only ever appears once, in the terminal `result` frame's `total_cost_usd`. There is no way to meter spend mid-run from the stream; the ceiling has to be enforced by the same process that's actually spending, i.e. `claude` itself.
3. **Full-lifetime machine billing, settled at true-destroy.** Machines are tagged at birth with identity metadata (`sub`/`sessionId`/`nodeId`, baked into Fly's `config.metadata` at create — see `fly-provider.ts`'s `SANDBOX_SUB_METADATA_KEY` etc.). Whoever actually destroys the machine — the TTL sweep (`sandbox-sweep.ts`) on a normal finish, or `CloudAgentRunner`'s error-path `finally` — reads that metadata back and bills `create → now` wall-clock seconds × `FLY_MINUTE_RATE_USD` × `creditMultiplier` via `UsersService.billMachineUsage`. This is idempotent per sandboxId through `DynamoRepository.putMachineBill`'s conditional-create guard (a `MachineBillItem` keyed by sandboxId; a second attempt to bill the same sandbox — e.g. a racing sweep tick — gets a `ConditionalCheckFailedException` and is a silent no-op), which is what makes "either the sweep or the runner may destroy-and-bill, don't coordinate which" safe.

**Billing basis is `total_cost_usd × creditMultiplier`, not token-count × `priceFor`.** `total_cost_usd` is cache-accurate (accounts for prompt-cache discounting the way a manual token×price calculation doesn't) and is present in the `result` frame on both a normal finish and a budget-stopped run — a budget stop zeroes the reported usage token counts but still carries a real `total_cost_usd` for the partial work done. Token×`priceFor` survives only as a fallback for the one case that emits no `result` line at all: a wall-clock `CLAUDE_TIMEOUT_MS` kill. That fallback bills ~$0 in tokens (none were ever observed) — the machine itself is still billed in full by part 3 regardless, so the run isn't free, just under-billed on the LLM-token component.

**Model correctness ("opus plans, sonnet implements") was also a real bug, not just a naming cleanup.** Before this, cloud CODE runs let the sandbox's `claude` CLI pick its own default model while the API billed against whatever `dto.model` had resolved to — the two silently disagreed (the API could bill haiku rates for a run the CLI actually served on opus). Cloud CODE runs now force `CLOUD_CODE_MODEL_ID` (sonnet) end to end: passed to the CLI as `--model` and used for the hold/ceiling/usage-event bookkeeping, so what's billed is what ran. `PLAN` nodes (via `createMixNode`'s `dto.plan`) separately force `PLAN_MODEL_ID` (opus), not user-overridable — the other half of the same product decision.

**New schema:** `HoldItem`, `MachineBillItem`; `UsageEventItem` gained `runId`, `machineSeconds`, and a `'MACHINE'` kind (alongside the existing `QUERY`/`DEEPER`/`ASK`/`MIX`/`PLAN`/`CODE`). New config: `FLY_MINUTE_RATE_USD` (default `0.0009`), `MAX_RUN_COST_USD` (default `1.00`), `SANDBOX_HOLD_USD` (default `1.00`).

**Tolerated bounded gaps** — consistent with the codebase's existing no-conditional-write-locking overdraft posture (see fork.ai ADR-0004's own tolerance for this):
- A machine-cost overdraft window on the order of cents: the machine keeps running (and billing) for whatever minutes elapse between the run finishing and the sweep actually destroying it.
- A crashed run's token cost is never billed (never observed, so nothing to charge) — the hold is still released and the machine is still billed in full, so the gap is bounded to the LLM-token component of that one run.
- A wall-clock-timeout run bills ~$0 in tokens for the same reason, machine cost unaffected.

**Live-verified (2026-07-13, real Fly Machines + real Anthropic API + a real private repo — not mocked):**
- A normal run: hold placed at start, reconciled at done to a net charge equal to the run's real `total_cost_usd × creditMultiplier`; the machine billed exactly once at sweep; a second sweep tick over the same (already-destroyed) sandbox is a confirmed no-op (idempotent via `putMachineBill`'s conditional create).
- A forced-tiny-budget run: stopped by `--max-budget-usd` with `budgetExceeded: true` reported, and charged the real partial `total_cost_usd` for the work actually done before the cutoff (not $0) — run on Sonnet, confirming the model-correctness fix held under the same test.

**Not yet built — frontend follow-ups only, backend is complete.** The backend plumbs `budgetExceeded` onto the node and onto both the `MACHINE` and `CODE` usage events, and running/final cost is fully computed and persisted — but nothing in the UI surfaces either yet (no running-cost readout during a stream, no "budget exceeded" indicator on a stopped run). Pure presentation work against data that already exists server-side.
